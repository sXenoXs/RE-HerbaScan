# Security Testing Plan — HerbaScan v0.9.3

**Testing Type:** Non-Functional — Security  
**Scope:** Authentication, Row Level Security (RLS), JWT handling, data exposure, SQL injection, deep link injection, and storage path traversal  
**Date:** March 7, 2026  
**Version:** v0.9.3

---

## Overview

Security tests validate that HerbaScan's data protection mechanisms — Supabase RLS policies, JWT verification, admin route guards, and input sanitization — function correctly and prevent unauthorized access or data manipulation. Tests are performed using curl, Supabase dashboard inspection, modified HTTP requests, and the Flutter app itself.

## Test Cases

| ST-SEC-001 | Unauthenticated Supabase access — `scans` table (private) | Verify that an unauthenticated HTTP request to the Supabase `scans` table SELECT endpoint returns an authorization error (RLS blocks unauthenticated reads), while `catalog_plants` SELECT (public read) returns data | Run: `curl -H "apikey: {ANON_KEY}" https://tsahfzmxqsgbxrrtbdnw.supabase.co/rest/v1/scans?select=*` (no `Authorization: Bearer` header); separately run the same for `catalog_plants` | `scans` SELECT with no auth token → HTTP 200 with empty array `[]` (RLS returns no rows) or HTTP 401; `catalog_plants` SELECT with no auth → HTTP 200 with plant data (public read policy enabled) | | | Supabase anon key alone does not bypass RLS; only `auth.uid()` policies match rows. | ST-SEC-002 | Non-admin user accesses `/admin` route (GoRouter guard) | Verify that a signed-in user with `role = "user"` (not admin) who navigates to `/admin` (via URL bar on web or deep link) is redirected to `/home?unauthorized=1` and the `AdminWebScreen` never renders | Sign in with a `role = "user"` account; on web, navigate to `https://app/admin` in URL bar; on mobile, attempt `context.go("/admin")` via debug | App redirects to `/home?unauthorized=1`; a SnackBar or message appears saying "Unauthorized access."; `AdminWebScreen` widget is never built/rendered | | | GoRouter redirect in `app_router.dart` calls `auth.refreshRole()` before allowing `/admin`. | ST-SEC-004 | JWT expiry during Railway scan — behavior with and without `SUPABASE_JWT_SECRET` | Verify two Railway JWT behaviors: (A) With `SUPABASE_JWT_SECRET` unset — requests without or with an expired token both return 200; (B) With `SUPABASE_JWT_SECRET` set — an expired Bearer token returns 401 | (A) Send `POST /identify` with no Authorization header; (B) Send `POST /identify` with `Authorization: Bearer <expired_token>`; repeat for both Railway configurations | (A) HTTP 200 regardless of token presence; (B) HTTP 401 "Invalid or expired token" for expired token; Flutter app falls back to offline CAM on 401 | | | Test scenario A with production Railway (recommended config — `SUPABASE_JWT_SECRET` unset). | ST-SEC-005 | SQL injection via Browse search field | Verify that entering a SQL injection payload in the Browse search field does not corrupt, drop, or expose the SQLite database; the search query uses parameterized bindings | In the Browse screen search field, enter: `'; DROP TABLE plants; --`; press search | Zero results returned (no plants match the injection string); SQLite database intact (plants still load normally after search); no crash; no `DatabaseException` in console | | | `DatabaseService` queries use `LIKE ?` with `[searchTerm]` parameters (not string interpolation). | ST-SEC-006 | Supabase Storage path traversal — blocked by RLS | Verify that an authenticated user cannot upload a file outside their own folder (`{user_id}/`) by crafting a path like `../../admin/malicious.jpg`; Supabase RLS policy must reject the upload with 403 | Using a modified API call (curl or Supabase JS client), attempt: `supabase.storage.from("herbarium-images").upload("../../admin/malicious.jpg", bytes)` | HTTP 403 or storage RLS rejection; file must NOT appear in any path other than the user's own `{user_id}/` folder; Supabase Storage dashboard confirms no stray file | | | RLS policy: `(storage.foldername(name))[1] = auth.uid()::text` enforced by migration `20260302000000_storage_herbarium_policies.sql`. Path traversal on Supabase Storage is normalized before the check, but test is still required. |
| ST-SEC-007 | `delete-user` Edge Function — unauthorized call rejected | Verify that calling the `delete-user` Edge Function without a valid Bearer token returns 401 and does NOT delete any user account | Call: `curl -X POST https://tsahfzmxqsgbxrrtbdnw.supabase.co/functions/v1/delete-user` with no Authorization header; separately call with a Bearer token for a different project | Both calls return HTTP 401; no user is deleted from Supabase Auth; Edge Function JWKS verification rejects the invalid/missing token | | | Edge Function verifies JWT via JWKS endpoint internally (`verify_jwt = false` in gateway; manual JWKS check inside function). No auth → 401. Wrong-project token → 401. |
| ST-SEC-008 | Deep link injection — fake auth callback token | Verify that a crafted `herbascan://auth/callback?access_token=FAKETOKEN123&type=recovery` deep link does NOT create a valid Supabase session; `AuthDeepLinkHandler` calls `getSessionFromUrl()` which validates the token server-side | Simulate a deep link delivery: on Android, use `adb shell am start -a android.intent.action.VIEW -d "herbascan://auth/callback?access_token=FAKETOKEN123&type=recovery" com.example.herbascan`; observe auth state | App opens but `getSessionFromUrl()` returns an error (Supabase rejects the fake token); `AuthProvider.isLoggedIn` remains `false`; no session is created; user remains on the current screen or is redirected to login | | | `AuthDeepLinkHandler` must call `Supabase.instance.client.auth.getSessionFromUrl(uri)` and handle the error gracefully without crashing. |
| ST-SEC-009 | Admin-only Supabase tables — non-admin INSERT blocked | Verify that a signed-in non-admin user cannot INSERT, UPDATE, or DELETE rows in `catalog_plants` (admin-only write) via the Supabase API | Using a non-admin access token, attempt: `supabase.from("catalog_plants").insert({ id: "hack-001", common_name: "Hacked Plant" })` | HTTP 403 or RLS violation error; no new row inserted; existing `catalog_plants` data unmodified | | | RLS policy on `catalog_plants`: INSERT/UPDATE/DELETE requires `public.is_admin()` to return true. Non-admin user's `is_admin()` returns false. |

## Notes

- All security tests should be performed against a **staging Supabase project** (not production) to avoid affecting real user data.
- SQL injection tests (ST-SEC-005) are safe to run on device since the payload only affects a local SQLite query.
- Deep link injection (ST-SEC-008) requires `adb` installed and USB debugging enabled.
- Document all results in a security test log; any failures should be treated as high-priority bugs before production release.
- Storage and Edge Function tests require valid Supabase credentials (anon key and a test user access token).
